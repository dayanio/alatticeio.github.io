出口节点：路由、DNS 与分流 ​

说明性文档 · 2026-09-24 配套设计：docs/superpowers/specs/2026-09-23-exit-node-dataplane-design.md（提供端转发）

文中的结论分三档：【实测】 在本项目环境里亲手验证过；【代码】 读代码得出；【推断】 合理判断但没有验证。

1. 一句话 ​

出口节点 = 一条 WireGuard 三层隧道 + 出口机器上的 NAT。

隧道只搬运 IP 包：它不认识 HTTP，不认识域名，也不知道你在访问 Google 还是百度。 这一点决定了本文里所有的设计取舍，也是它和 Clash 最大的区别（见第 6 节）。

2. 一个 HTTPS 请求的完整旅程 ​

以手机 Chrome 访问 https://www.google.com 为例，出口模式开启：

① DNS：先把 www.google.com 解析成 IP                 ← 第 3.2 节专门讲
② Chrome 对这个 IP:443 发起 TCP + TLS，发 HTTP 请求
      │
      ▼
手机系统 TCP/IP 栈：把请求切成 IP 包
      [IP头 src=10.96.0.4 dst=142.250.x.x | TCP | TLS 加密后的 HTTP 数据]
      │
      ▼
路由表：dst 落在 0.0.0.0/1 或 128.0.0.0/1（出口模式装的两条路由）
      → 交给虚拟网卡 utun，而不是 Wi-Fi / 蜂窝
      │
      ▼
隧道扩展（Network Extension）读出这个原始 IP 包 → 交给 Go 引擎
      │
      ▼
WireGuard：把「整个 IP 包」加密，装进一个 UDP 包
      [外层 IP：手机公网 → 出口公网 | UDP | WireGuard 密文]
      │  经过 Wi-Fi/蜂窝，穿过互联网（ICE 直连，或走 relay 中继）
      ▼
出口机器（香港）：WireGuard 解密，还原出内层 IP 包
      │
      ▼
出口内核：① FORWARD 放行  ② MASQUERADE：把源 10.96.0.4 改成出口自己的公网 IP
      │
      ▼
发往真正的 Google（对方看到的源是香港 IP）
      │
      ▼
回程：Google → 出口 → 内核按连接跟踪把目的地址改回 10.96.0.4
      → WireGuard 加密 → 发回手机 → 解密 → 写回 utun → 系统栈 → Chrome

HTTP 的数据是不是都进了隧道？ 是的，但准确地说是：所有匹配路由的 IPv4 包（TCP、UDP、ICMP，包括 DNS 和 QUIC）都进隧道，HTTP 只是 TCP 载荷。

两层加密的关系：

层谁和谁之间防谁
TLS（HTTPS 自带）Chrome ↔ Google出口节点也看不到 HTTPS 内容
WireGuard手机 ↔ 出口中间网络看不到你在访问什么

出口能看到：目的 IP、端口、流量大小。看不到 HTTPS 的内容（明文 HTTP 除外）。

哪些流量故意不进隧道 ​

这些是排除项，不排除会"自己吃自己"：

  1. 控制面地址（如 101.36.119.12）：NE 设置里把它列为排除路由，否则手机连不上控制面，也就收不到"取消选择"的推送。【代码】PacketTunnelProvider.swift 的 excluded.append(hostIP)。
  2. 隧道扩展自己发出的包（WireGuard 的 UDP、中继的 TCP）：如果它们也被路由回隧道，就会"外层包被当作内层包再加密一次"，无限循环。Mac 版用「socket 绑定物理网卡」（bind interface: en0）避免；iOS 版目前没有这一步。【代码】
  3. 局域网网段：有更具体的路由，不进隧道。
  4. IPv6：目前没有接管，有 IPv6 的网站可能绕过出口直连。【代码】这是已知缺口。

3. 三件事要分开想 ​

出口节点其实同时在做三件互相独立的事，很多困惑来自把它们混在一起：

层问题由谁决定
路由哪些包进隧道？手机的路由表（includedRoutes / excludedRoutes）
DNS域名怎么变成 IP？手机的系统 DNS 设置
NAT包到了出口怎么出去？出口机器的 iptables

3.1 路由 ​

出口模式下，NE 设置里的路由是：

included:  10.96.0.0/24      overlay 网段（始终在隧道里）
           0.0.0.0/1         ┐ 合起来就是 0.0.0.0/0
           128.0.0.0/1       ┘ 拆成两半，比系统默认路由更具体，所以必胜
excluded:  控制面 IP/32

为什么不直接写 0.0.0.0/0？因为单个 /0 会被系统降级，抢不过物理网卡的默认路由。WireGuard 官方客户端也是这么做的。【代码】

3.2 DNS ​

为什么必须单独处理？ 隧道不认识域名。手机要先知道 www.google.com 的 IP，才有后面的包。

如果不处理会怎样？【实测】手机用运营商的 DNS，google.com 被污染成一个假的 Facebook 地址（31.13.92.37、157.240.7.20）。抓包里能看到手机对这两个地址反复重试上百次 SYN，永远没有回应。这是典型的 DNS 污染特征。

关键概念：DNS 设置只决定"往哪发"，进不进隧道由路由决定。

系统 DNS 设置（NEDNSSettings）  →  "解析域名时，把查询发给 8.8.8.8"
                                        │
                                        ▼   系统发出一个普通 UDP 包：
                                        │   10.96.0.4:随机端口 → 8.8.8.8:53
                                        ▼
                                  查路由表：8.8.8.8 落在 0.0.0.0/1
                                        │
                                        ▼
                                  交给 utun → 进隧道 → 出口 → 8.8.8.8

所以"DNS 进了隧道"不是 DNS 设置的魔法，纯粹因为 DNS 服务器的地址落在了隧道的路由范围里。这是 3.2 节之后所有方案的核心。

matchDomains 的坑【实测】：

写法效果
matchDomains = nil不会让隧道 DNS 成为默认解析器，域名照旧走运营商 DNS（Mac 上 scutil --dns 仍显示物理 DNS 114.114.114.114）
matchDomains = [""]隧道 DNS 成为默认解析器，所有域名都走它（WireGuard 官方同款）

3.3 NAT（出口机器） ​

出口 agent 在检测到自己宣告了路由后，幂等地装这几条（internal/agent/provision/exit_gateway.go）：【代码】

sysctl net.ipv4.ip_forward=1
iptables -A FORWARD -i wf0 -j ACCEPT                       # 隧道进来的放行
iptables -A FORWARD -o wf0 -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT   # 回程放行
iptables -t nat -A POSTROUTING -o <默认出网卡> -s 10.96.0.0/24 -j MASQUERADE      # 源地址改写

4. DNS 的几种做法 ​

4.1 云主机"有 DNS"是什么意思 ​

先澄清一个容易混淆的点。【实测】你的出口机器：

检查结果
/etc/resolv.conf10.8.255.1、10.8.255.2（云厂商内网 DNS），备用 114.114.114.114
本机解析 www.google.com返回真实 Google 香港地址，无污染
端口 53 有没有进程在监听没有
  • "有 DNS"指它有上游可以问（resolv.conf 是客户端配置）；
  • 它没有一个在监听 53 端口、能回答别人查询的 DNS 服务。

4.2 方案 A：把公共 DNS 设成系统 DNS（当前方案） ​

手机 ──(隧道)──▶ 出口(只做转发+NAT) ──▶ 8.8.8.8（互联网上的公共 DNS）
                    ▲                        真正回答的是它
                 不需要 DNS 服务
  • 系统 DNS = 8.8.8.8、1.1.1.1，matchDomains = [""]。
  • 出口只是路由器，回答问题的是互联网上的 8.8.8.8。出口上不需要任何 DNS 服务。
  • 引擎不参与：DNS 包和其他任何包一视同仁。
  • 代价：出口模式期间 *.lattice 短名解析不了（用 overlay IP 直连不受影响）。
  • 状态：【实测】在 iPhone 上，Chrome 通过出口访问到了 Google 的真实服务器（142.250.x.x/142.251.x.x 完成握手，QUIC 在走）。 注意：那次抓包里没抓到 UDP 53（Chrome 可能用了自己的加密 DNS 或命中缓存），所以"DNS 包进了隧道"没有被直接抓到，只能从"连上的是真实 Google 地址"间接说明解析是干净的。

4.3 方案 B：出口节点自带 DNS 转发器 ​

手机 ──▶ 10.96.0.8:53（出口的 overlay 地址） ──▶ 出口把查询转给 10.8.255.1（云内网 DNS）
          走 overlay 路由，永远在隧道里
  • 系统 DNS = 出口的 overlay 地址。出口 agent 新增一个监听 10.96.0.8:53 的小转发器。
  • 不依赖全局路由：overlay 路由 10.96.0.0/24 永远存在。
  • 上游是云厂商内网 DNS（【实测】从 overlay 地址 10.96.0.8 去问能通），比公网 8.8.8.8 更近。
  • 可以顺手做缓存、日志、回答 *.lattice。
  • 代价：出口要多跑一个组件；出口离线时 DNS 也跟着失效（A 反而更稳：出口离线时服务端撤掉 0.0.0.0/0，DNS 自然回到手机自己的网络）。

4.4 方案 C：引擎做包级 DNAT ​

  • 系统 DNS 保持虚拟地址 10.96.0.1；引擎收到发往它的非 lattice 查询，只改目的地址成真实解析器后原样转发，回程再把源地址改回。
  • 全程是"改地址"，不自己开 socket、不合成应答。
  • 代价：引擎要维护改写状态表，客户端变复杂。

4.5 方案 D：fake-ip（Clash 的做法） ​

  • 本地 DNS 直接返回假地址 198.18.x.x，等应用连过来，再反查出它想访问的域名，交给远端解析。
  • 优点：能按域名分流。
  • 前提：必须能在用户态还原出 TCP 连接（需要内置协议栈）。这是仓库里 2026-09-23-gvisor-embedded-networking-design.md 那条线，是大改造。

4.6 场景对照 ​

场景A（8.8.8.8）B（出口自带）C（引擎 DNAT）D（fake-ip）
只做全局出口（现在）够用没必要没必要没必要
出口离线服务端撤路由，DNS 回本地，App 仍能用DNS 随之失效同 B同 B
国内直连（IP 分流）8.8.8.8 在国外，仍进隧道，无问题overlay 地址，不受排除路由影响同 B—
国内域名要走国内 DNS做不到做不到（要客户端分流）可做（引擎里判断域名）能做
*.lattice 短名不可用可用可用可用
依赖第三方解析器是（8.8.8.8）否可选否
客户端改动最小需要传出口地址大最大
出口改动无加转发器无无

4.7 结论 ​

  • 现阶段用 A，最简单，已在手机上验证。
  • 不要为了"出口有 DNS"而做 B：出口上没有 DNS 服务是正常的，A 根本不需要它。
  • B 值得做的时机：出口访问 8.8.8.8 变慢或被限、想在出口做 DNS 日志/缓存、需要在出口模式下保留 *.lattice。

5. "国内直连、国外走隧道"能做吗 ​

能，分两种：

5.1 按 IP 分流（推荐先做） ​

全局路由照装 0.0.0.0/0，再把中国大陆 IP 段放进 excludedRoutes，这些地址走物理网络直连。这是 WireGuard 客户端做"绕过大陆"的标准做法。

  • 做法：内置一份大陆 IPv4 段（合并后约几千条），App 加"国内直连"开关，Mac/iOS 的 NE 设置里生效。
  • 优点：走内核路由，国内流量完全不经隧道，没有额外性能开销，不碰引擎。
  • 局限：
    • 只认 IP，不认域名，不能写"google.com 走代理、baidu.com 直连"；
    • 几千条排除路由在 iOS NE 上是否稳定，需要实测【推断】；
    • 国内域名仍被 8.8.8.8 解析（经香港），可能返回境外节点，访问变慢；要解决需要 DNS 也按域名分流；
    • 列表需要定期更新。

5.2 按域名/规则分流（真正的 Clash 体验） ​

必须在用户态还原出 TCP/UDP 连接，才知道每个连接要访问的域名。这需要内置协议栈（gVisor），是另一条线，不是加个开关。

6. 与 Clash、Tailscale 的对比 ​

Clash本项目（WireGuard 出口）Tailscale（出口节点）
工作层应用层：还原连接后代理网络层：搬运 IP 包网络层：搬运 IP 包
认识域名是否否（DNS 单独处理）
系统代理系统代理模式改系统代理设置；TUN 模式不改不改，用虚拟网卡 + 路由不改
DNSfake-ip / 远端解析系统 DNS 指向解析器，靠路由进隧道自带 DNS 转发器，出口模式下转给出口
防回环内部处理Mac 绑物理网卡；iOS 未做绑物理网卡
IPv6支持未接管一并接管

说明：Clash 的部分来自你机器上的实际现象（198.18.0.x 是 Clash 的 fake-ip；scutil --proxy 显示系统代理关、说明你用 TUN 模式）。Tailscale 一栏是我对它设计的了解，没有逐项核实【推断】。

结论：本项目的架构方向和 Tailscale/WireGuard 是同一类，不是 Clash 那一类。 出问题的是周边实现，不是方向。

7. 我们踩过的坑（症状 → 原因 → 修复） ​

#症状原因修复
1选了出口整机断网，utun5 的 Ipkts=0交付循环只在攒够 64 个包时才 writePackets，单个回包永远卡住非阻塞取空后立刻 flush（bd151981）
2google.com 被解析成假的 Facebook IPmatchDomains=nil 没让隧道 DNS 成为默认解析器，域名走了运营商 DNSmatchDomains=[""]，系统 DNS 设为公共解析器（bd151981）
3隧道连上几秒就掉线，每秒几千个包引擎拦截 DNS 只看端口 53、不看目的地址，把自己转发的上游查询又拦回来，无限循环只拦截发往 10.96.0.1 的查询，附回归测试（bd151981）
4App 首页报 LatticeAPIError控制面把未登录返回成 HTTP 200 + 响应体 {"code":401}，App 只处理 HTTP 401，静默重新登录永远不触发响应体 code==401 也当未登录（bd151981）
5出口离线时消费端整机断网服务端仍给消费端下发 0.0.0.0/0出口离线就不下发它的宣告路由（6b41ebd3）
6出口重启后消费端长时间停在无出口状态在线状态变化没有通知消费端出口上下线时推送 netmap 更新（7616c357）
7手机隧道起不来：public key mismatch手机的设备密钥丢失，服务端拒绝"换密钥"删除旧 peer，重新入网（这次是排查过程中误删了设备容器导致，属于操作失误）
8手机引擎日志 190 MBdebug 级别 + 追加打开，从不清理启动时超过 5 MB 就清空（bd151981）
9Mac 上开全局后整机断网Clash TUN 和 Lattice 的全局路由同时存在，互相捕获对方的流量，形成环路未修复，测试时必须先关掉 Clash TUN

8. 当前状态与路线 ​

已验证（iPhone）：全局出口 + 干净的域名解析 + Chrome 访问 Google。

未验证：

  • Mac 上的全局出口（需要先关 Clash TUN，测试时会影响本机网络）；
  • 方案 A 的 UDP 53 是否确实进入隧道（需要在没缓存的域名上抓包确认）。

建议路线：

  1. 继续在手机上使用方案 A，观察稳定性；
  2. 给 iOS 版补上「socket 绑定物理网卡」，与 Mac 对齐；
  3. 补 IPv6 接管，避免绕过出口；
  4. 做"国内直连"的 IP 分流（5.1）；
  5. 之后再评估方案 B（出口自带 DNS）或 gVisor 路线（5.2）。

10. 验证方法 ​

bash
# 手机是否走了出口（在出口机器上）
tcpdump -ni wf0 -nn "host <手机 overlay 地址>"

# 手机的 DNS 包是否进了隧道（应看到 源=手机overlay 目的=8.8.8.8:53）
tcpdump -ni wf0 -nn "host <手机 overlay 地址> and udp port 53"

# Mac 上：隧道网卡是否在收包（Ipkts 应持续增长，为 0 说明下行没交付）
netstat -I utunN -bn

# Mac 上：某个地址走哪张网卡
route -n get 8.8.8.8

# Mac 上：系统当前用的 DNS（出口模式下应是 8.8.8.8 / 1.1.1.1）
scutil --dns | head -20

# 出口机器上：转发和 NAT 规则
cat /proc/sys/net/ipv4/ip_forward
iptables -t nat -S POSTROUTING
